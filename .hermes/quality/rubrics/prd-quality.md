# PRD Quality Rubric

## Purpose

Evaluate whether a PRD can guide product, UX, engineering, and verification work.

## Required Inputs

- PRD
- Problem statement
- Target users
- MVP scope
- Success metrics

## Quality Dimensions

| Dimension | What To Check |
| --- | --- |
| Problem clarity | The PRD explains the problem before the solution. |
| Scope control | Goals, non-goals, and MVP boundary are explicit. |
| Requirements quality | Functional and non-functional needs are testable. |
| Metrics | Success metrics reflect user and business outcomes. |
| Risk visibility | Assumptions, dependencies, and rollout concerns are visible. |

## 5-Point Scoring Criteria

| Score | Criteria |
| --- | --- |
| 1 | Feature list with no problem, users, or criteria. |
| 2 | Partial PRD with unclear scope or untestable requirements. |
| 3 | Usable PRD with some gaps in metrics or risks. |
| 4 | Clear PRD ready for backlog translation. |
| 5 | Strong PRD with traceability, metrics, scope discipline, and validation plan. |

## Pass/Fail Threshold

Pass at 4 or higher. Fail if goals, non-goals, or acceptance signals are missing.

## Common Failure Patterns

- Reads like a solution pitch instead of a decision document.
- Includes too many MVP features.
- Uses vague requirements like "easy to use".
- Leaves data, API, permissions, or rollout risk undefined.

## Improvement Guidance

Add problem, target user, goals, non-goals, requirements, metrics, MVP boundary, risks, and rollout plan.

## Example Of A High-Quality Output

"The PRD defines a learner risk dashboard for course managers, names inactivity and low progress as core signals, excludes automated nudges from MVP, and uses reduced weekly reporting time plus earlier learner intervention as success metrics."
