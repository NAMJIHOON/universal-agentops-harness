# Backlog Quality Rubric

## Purpose

Evaluate whether a backlog is sequenced, sliced, and ready to translate into implementation tasks.

## Required Inputs

- Sprint plan
- User story map
- MVP scope
- Acceptance criteria
- Dependencies and risks

## Quality Dimensions

| Dimension | What To Check |
| --- | --- |
| User-value slicing | Stories deliver visible user outcomes. |
| Sequencing | Dependencies and order are practical. |
| Acceptance criteria | Stories are testable. |
| Risk mapping | Technical, UX, data, and release risks are noted. |
| Delivery readiness | Stories can become Codex tasks. |

## 5-Point Scoring Criteria

| Score | Criteria |
| --- | --- |
| 1 | Backlog is a feature dump. |
| 2 | Stories exist but are too large or unclear. |
| 3 | Usable backlog with some missing criteria or dependencies. |
| 4 | Clear delivery backlog ready for Codex translation. |
| 5 | Strong backlog with sequencing, risks, acceptance criteria, and verification hints. |

## Pass/Fail Threshold

Pass at 4 or higher. Fail if stories are not testable or implementation-ready.

## Common Failure Patterns

- Splits work only by technical layer.
- Leaves dependencies hidden.
- Uses vague story titles without acceptance criteria.
- Mixes discovery questions with implementation tasks.

## Improvement Guidance

Slice by workflow step, user role, risk, or release boundary. Add acceptance criteria and dependencies.

## Example Of A High-Quality Output

"The backlog starts with course data setup, then readiness checklist, learner risk table, issue queue, and export. Each story has user value, criteria, risk, and verification expectations."
