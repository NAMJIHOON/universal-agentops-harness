# Pain Point Quality Rubric

## Purpose

Evaluate whether user pains are specific, evidence-based, and useful for product decisions.

## Required Inputs

- Pain point map
- Current workflow
- User notes or evidence
- Prioritization criteria

## Quality Dimensions

| Dimension | What To Check |
| --- | --- |
| Specificity | Pain is tied to a workflow step. |
| Evidence | Pain has source notes, data, or observed behavior. |
| Severity | Impact is clear enough to prioritize. |
| Frequency | Repetition or scale is described. |
| Opportunity fit | Pain can inform solution direction. |

## 5-Point Scoring Criteria

| Score | Criteria |
| --- | --- |
| 1 | Generic complaints without workflow context. |
| 2 | Some pains listed, but evidence and impact are weak. |
| 3 | Usable pain map with basic prioritization. |
| 4 | Clear pains linked to workflow, users, evidence, and severity. |
| 5 | Strong root-cause view with opportunity areas and validation questions. |

## Pass/Fail Threshold

Pass at 4 or higher. Fail if pains are not tied to users or workflow steps.

## Common Failure Patterns

- Confuses internal preferences with user pain.
- Lists symptoms without root-cause hypotheses.
- Ignores workarounds users already use.
- Prioritizes based on opinion only.

## Improvement Guidance

Map each pain to current workflow, user quote or evidence, business impact, and validation question.

## Example Of A High-Quality Output

"During weekly reporting, course managers spend 2 to 4 hours reconciling LMS exports and issue logs. The pain is frequent, high-severity, and creates late intervention for inactive learners."
